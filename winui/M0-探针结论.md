## 探针①描边 2.5 vs 3：改3，已用像素级证据确认

不靠肉眼，用截图逐列扫描深棕描边像素宽度：

| BorderThickness | 实测宽度 |
| --- | --- |
| 2.5 | **3px** |
| 3 | **3px** |

**2.5 被栅格化成了 3，与直接写 3 完全同宽。** 计划里「描边 2.5→3」的偏离零视觉代价，换来整数网格的一致性。决策成立，Palette.xaml 里`ThinEdge`/`CardEdge` 值写3。

## 探针③ Composition `Translation` 动画：跑在 compositor 线程，不占 UI 线程

**两条独立证据：**

**a) 位移实测** —— 相隔 2 秒的两帧截图做差，云层区域：
```
差异包围盒 (760, 2, 1824, 59)，显著变化像素 6910
=> 2 秒水平位移约 1064px
```
肉眼可见云从左飘到右。三朵云速度不同（18s / 26s / 34s 过场），符合预期。

**b) UI 线程抖动实测** —— DispatcherTimer 250ms 间隔，连续10 秒：

| t | DispatcherTimer 最大抖动 |
| --- | --- |
| 2s | 33.9ms |
| 4s | 33.9ms |
| 6s | 33.9ms |
| 8s | 33.9ms |
| 10s | 33.9ms |

**抖动值从 2s 起恒定在 33.9ms、不再增长** —— 那是启动期一次性开销（JIT + 首帧），不是动画的持续负担。动画期间UI 线程没被拖慢。

**意义**：背景层 60 个元素（3个 Path 云 + 6 片叶）与后台 diff 的 CRC32 计算可以安全共存。这正是选 `UIElement.StartAnimation` 而非 XAML `Storyboard` 的理由。

> **M1 补注**：本次 1064px 位移是用 **`Offset`** 路线量出来的。当时能跑通是**侥幸**——
> 云在 `Canvas` 里布局几乎不变，`Offset` 才没被布局 pass 覆盖（stomping）。
> 详见第 7b 条。方向结论（不占 UI 线程）依然成立，**但实现路线必须换成
> `SetIsTranslationEnabled` + `Translation`**。

## 踩坑记录（这部分是M0 最大的产出）

### 1. unpackaged 下不能设 `Application.RequestedTheme`

设了抛 `COMException 0x80131515`，发生在 `OnLaunched` 内，表现为**双击即退、窗口都不出**。`dotnet build` 全绿也照样崩。

**正确做法**：把 `RequestedTheme="Light"` 写在视觉树根元素（MainWindow 的根 Grid）上。

另外类型容易混：`Application.RequestedTheme` 是 `ApplicationTheme`，`UIElement.RequestedTheme` 是 `ElementTheme`。

### 2. MSIX 工具链在 .NET 10 下直接编译失败

`EnableMsixTooling=true`（哪怕只做Debug build）会触发 `WinAppSdkValidateAppxManifestItems`，该任务加载 `System.Security.Permissions 8.0.0.0` 失败 → `MSB4018`，连 Debug 都过不去。

本项目全程 unpackaged，**直接在 csproj 里写 `<EnableMsixTooling>false</EnableMsixTooling>`**，不靠命令行覆盖。

> 与 MarukoBox 的差异：它保持 true 靠命令行压。本项目没这个包袱。

### 3. `StaticResource` 拼错是运行期炸，且不报错只是「窗口出不来」

漏了 `BrushBgGradA`（只定义了 Color `McBgGradA`，没定义对应画刷）→ `XamlParseException: Cannot find a Resource with the Name/Key BrushBgGradA`，在 `MainWindow..ctor` 抛，窗口完全不出现。

**已在 tools/ 加了交叉校验脚本的思路**：XAML 里引用的每个 `StaticResource` key 都要能在资源字典里找到。M1 之后把这个校验固化成构建步骤，别等运行期才发现。

### 4. XML 注释里不能出现连续两个减号

写 CSS 变量原名（如 `--muted`）进注释 → `WMC9997`。注释里描述 CSS 变量时别写 `--` 前缀。

### 5. WinUI 3 没有 `ClipToBounds`

`Border`/`Grid`/`Panel` 都没有这个属性。要裁剪给内容元素加 `Clip`：

```xml
<Canvas.Clip>
    <RectangleGeometry x:Name="CloudClip" Rect="0,0,900,70" />
</Canvas.Clip>
```

注意宽度必须跟随窗口变化动态更新（`SizeChanged` 里改 `Rect`），否则窗口拉宽后云被裁成一条。

### 6. `Window` 没有 `Loaded` 事件

`Loaded` 是 `FrameworkElement` 的，WinUI 3 的 `Window` 不是。要挂在根 Grid 上。

### 7. Composition 的 `Translation` 默认未启用（此条曾被误判，M1 已订正）

> **订正说明（2026-10-09，M1）**：本条原先写的是
> 「`Visual` **没有** `Translation` 属性（UWP 时代有，WinUI 3 移除了）」——
> **这个结论是错的**，且它直接误导了 `PixelBackground.xaml.cs` 的初版实现，
> 导致 M1 冒烟时抛 `ArgumentException: ... Context: Translation`。
> 下面重写为查证后的事实。

微软文档列出的 `Microsoft.UI.Composition.Visual` **官方可动画属性只有 9 个**：

> Size / Offset / Opacity / Orientation / CenterPoint / RotationAngle /
> RotationAngleInDegrees / RotationAxis / TransformMatrix

清单里确实**没有** `Translation`。但结论不是「被移除了」，而是 ——

**`Translation` 是默认未启用的属性**，必须先对元素调用：

```csharp
ElementCompositionPreview.SetIsTranslationEnabled(element, true);
```

它才会被创建。注意这个方法是 **`static`**（没有 Visual 实例可传），
且**必须直接调在要动画的那个元素上**，调在父元素上对子元素无效。
漏掉这步 → `StartAnimation("Translation", …)` 就抛
`The specified property was not found or cannot be animated. Context: Translation`。

启用后还建议预热一次（handoff visual 是异步创建的，有交接时序）：

```csharp
visual.Properties.InsertVector3("Translation", Vector3.Zero);
```

**为什么不能用 `Offset` 代替**（这才是本条真正该沉淀的经验）：

| | `Offset` | `Translation` |
| --- | --- | --- |
| 性质 | XAML 渲染引擎写的**绝对位置** | 渲染期 post-layout 的**叠加位移** |
| 布局 pass 时 | 会被整个覆盖（微软博客称 *stomping*），并**打断正在跑的动画** | 框架层对它「无感知」，永不被覆写 |

文档原话：`Translation always applies as an additive to the current Offset.`

**另一条实测事实保留**：`CompositionPropertySet` 在 WinAppSDK 2.5.1 的 C# 投影里
**确实没有** `GetVector3()`，也没有字符串索引器。所以调试 compositor 动画别读属性，
用两帧截图做差（见第 8 条）。但这是「读不到」，**不等于**「属性不存在」——
本条原先正是把「读不到」错误推导成了「不存在」，两者必须分清。

### 7b.探针③ 的1064px 是用 `Offset` 测出来的 —— 属于侥幸有效

探针③ 当时量到「3 个云 2 秒位移 1064px、UI 线程抖动恒定 33.9ms」，结论方向正确
（Composition 动画不占 UI 线程），但**当时走的是 `Offset` 路线**。

之所以没暴露 stomping 问题：云被放在 `Canvas` 里，布局几乎不变，
所以 `Offset` 一直没被布局 pass 覆盖。**换成会重排的容器（StackPanel/Grid 内换算位置）
就会立刻断掉动画。**

迁移到正式控件 `PixelBackground` 时改写成了 `Translation`，才炸出上面的
`ArgumentException`。所以本项目的正确路线是
**`SetIsTranslationEnabled` + `Translation`**，而不是退回 `Offset`。

### 8. 图像差分的坐标系必须对齐原图分辨率

第一轮差分给出「两帧零差异」的假阴性，根因是裁剪坐标照着**缩放后的预览图**估，量到了空白背景区。改用真实分辨率坐标后测出 1064px 位移。

**教训**：预览图只能用于肉眼观察，任何像素级测量必须用原图坐标。

### 9. M1 新增：`WindowsPackageType` 空值会静默毁掉 unpackaged 发布

本条与第 3、4 条同类 —— **构建日志全绿、一个字都不提示，但产物是坏的**。

探针实测：`<EnableMsixTooling>false</EnableMsixTooling>` **并不会**让
`WindowsPackageType` 变成 `'None'`，它的值是**空字符串**（压根没被定义）。
当时 csproj 里没有显式写这个属性，连带两个后果：

1. **运行时** —— 不走 unpackaged 路径，WinAppSDK 的 native 运行时
   （`Microsoft.ui.xaml.dll` 等）不打包进发布目录，
   启动即 `COMException 0x80040154 (REGDB_E_CLASSNOTREG)`。
2. **构建时** —— 依赖该属性的 Target 静默跳过，
   `.xbf` 与 `resources.pri` 全都不进发布目录。

而 csproj 里那个拷贝 Target 的 Condition 写的正是
`'$(WindowsPackageType)' == 'None'` —— **永远为假**，从来没执行过。

**修法**：csproj 里显式写 `<WindowsPackageType>None</WindowsPackageType>`
（连同 `WindowsAppSDKSelfContained` / `SelfContained`），
并重新 `mv` 掉 obj/bin 强制全量重建 —— 属性变更必须重建才生效。

**教训**：`EnableMsixTooling` 与 `WindowsPackageType` 是**两个独立开关**，
关掉前者不会顺带设置后者。凡是靠「== 'None'」判断 unpackaged 的地方，
都要先确认这个属性真的有值。

### 10. M1 新增：WinUI 没有 z-index，XAML 声明顺序即叠放层次

云和叶的动画在跑，但截图里**完全看不见**，两帧差分也是 0。

根因：主体 `Grid` 设了不透明渐变 `Background`，而它在 XAML 里声明在
`PixelBackground` **之后** —— WinUI 3 没有 z-index，**后声明的盖在上面**，
于是整层背景被压得严严实实。动画照跑，只是渲染在最底下。

修法：渐变底色提到 `RootGrid`，主体 `Grid` 改 `Background="Transparent"`。
层级变为 ① 根渐变 → ② 云与叶 → ③ 主体内容（透明）。

**教训**：这类"界面全对但某层不见了"的症状，先查叠放顺序，再查动画代码。
CSS 里的 `z-index` / `body` 背景语义在 WinUI 里没有对应物，必须显式排好层级。
**同时**：肉眼看不见的东西要用两帧差分证明它到底有没有在动 ——
本例若不做差分，会误判成"动画 API 又坏了"，从而继续在错误的层面排查。

### 11. M1 新增：`Tapped` 会冒泡 —— 整区可点 + 子控件各自有点= 弹两次

点「浏览文件…」弹出**两个**文件选择窗（Master 2026-10-09 实测发现）。

拖放区 Border 挂了 `Tapped`（「点哪儿都是选文件」，对应 CSS 的整块可点），
内部按钮另挂 `Click`。WinUI 的 `Tapped` **会冒泡**：

```
点按钮 → Button.Click  → PickAndLoadAsync()   第 1 次
       → 冒泡到 Border → Tapped → PickAndLoadAsync()   第 2 次 → 两个窗口
```

原先代码已排除过 `TextBox`，但漏了 Button，所以复现稳定。

**修法（两层）**：

1. `OnDropZoneTapped` 里判断 `e.OriginalSource` 是否
   `ButtonBase` / `TextBox`，是则放行。
   用**基类**而非具体控件类型 —— 一次覆盖 Button / HyperlinkButton /
   CheckBox / RadioButton 等，将来加任何按钮都不用回来补判断。
2. `PickAndLoadAsync` 加**重入锁**。第一层是"按控件类型排除"这种被动防御：
   只要将来某个控件又触发同一入口、或用户连点两下，还是会弹第二个。
   加锁把"最多一个"从"依赖调用方正确"变成"由方法本身保证"。
   **锁必须覆盖 await 期间** —— `PickSingleFileAsync` 会把控制权交回事件循环。

**教训**：WinUI 的路由事件**默认冒泡**，不像 DOM 那样默认不冒泡。
"容器整体可点 + 内部控件也有 handler"是最容易重复触发的组合。
凡是容器与子控件共享同一入口，都要用 `e.OriginalSource` 做一次归属判断。

## 工具产物

`winui/tools/capture_window.py` —— 按窗口标题抓图，**不抢前台**。

用 `PrintWindow(PW_RENDERFULLCONTENT)` 而非 `ImageGrab.grab(bbox)`：
- `ImageGrab` 抓的是屏幕像素，窗口被别的窗口盖住就抓到别人（本轮第一次抓到的是正在前台的游戏）
- `SetForegroundWindow` 在别的应用抢焦点时会失败（Windows 前台锁）
- `PrintWindow` 让窗口自己画进 DC，不依赖可见性/前后台关系，不干扰用户正在做的事

```bash
python winui/tools/capture_window.py "<标题片段>" "<输出png>"
```

## M0→M1 的结论

计划里的**唯一高风险项**（`RotationY` 角标翻转）已在决策阶段砍掉 —— 现在看来是对的：RotationY 那条路要读/驱动 Composition 的 `Rotation`/`RotationAxis`，正好撞上第7 条坑（投影里根本没有这些易用属性），风险确实高。

**可以放心开工 M1**，视觉调优从M1 正式开始。
